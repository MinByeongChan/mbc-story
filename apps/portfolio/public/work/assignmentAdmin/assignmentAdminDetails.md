## 개요

작업자, 일정, 이관과 배정 현황을 지도·목록·캘린더로 확인하고 조정하는 코웨이 내부 운영 도구입니다. 2022년 초기 구축에 참여해 지도와 일정 화면을 만들었고, 2026년에 다시 맡아 상태 관리 구조를 Recoil에서 Zustand로 이관했습니다.

## 핵심 사례

### 반복 조회할수록 느려지는 지도, 메모리 누수 제거

배정 현황을 지도에서 반복 조회할수록 화면이 느려지고 브라우저 메모리가 계속 늘어났습니다. 체감이 아닌 수치로 원인을 확인하기 위해 DevTools Heap Snapshot으로 조회를 5회 반복 측정했고, 조회마다 지도 인스턴스가 새로 생성되면서 detached DOM이 조회당 약 290개씩 쌓이는 것을 확인했습니다.

지도 인스턴스를 싱글턴으로 관리하고 조회 시에는 마커와 레이어만 갱신하도록 바꿔 **detached DOM을 100%(조회당 약 290개→0개) 제거했습니다.** 측정 방법은 팀에 공유해 이후 지도 화면 성능 이슈를 같은 기준으로 확인할 수 있게 했습니다. 무거운 화면일수록 체감보다 측정값으로 원인을 좁혀야 한다는 것을 배웠습니다.

### 회귀 0건으로 끝낸 Recoil → Zustand 이관

유지보수가 중단된 Recoil의 수십 개 Atom과 Selector가 화면 곳곳에 얽혀 있어, 한 번에 바꾸면 기존 동작이 조용히 바뀔 위험이 컸습니다.

변환 전에 기존 동작을 그대로 기록하는 Characterization Test를 먼저 작성하고, strangler 브리지 패턴으로 기존 인터페이스를 유지한 채 6단계로 나눠 기능별 Zustand Store로 옮겼습니다. 서버 상태와 자동 새로고침은 TanStack Query로 분리하고, 파생 데이터 Selector는 `useMemo`와 순수 유틸로 전환했습니다. 직접 만든 라이브러리 마이그레이션 AI 스킬을 활용하되 변환 결과는 기능 단위로 직접 검토했습니다.

**유닛 테스트를 45%(49개→71개) 늘리고 에러 경로 커버리지를 0건에서 9건으로 확보했으며, consumer 21개 파일을 수정하지 않고 회귀 0건으로 이관했습니다.** 기준 테스트 덕분에 QA에서 잡히지 않던 개발 미스 약 6건도 찾아냈습니다. 2022년에 참여했던 코드를 다시 옮기며, 영향 범위가 큰 작업은 동작을 테스트로 먼저 고정하고 작게 나눠야 한다는 것을 확인했습니다.
