# ABC Admin

2024.04 – 2025.12

## 서비스 내용

---

미국 법인의 WMS 물류 흐름과 회계 전표·원장을 중심으로 OMS, 작업 관리, 내부 시스템을 제어하는 통합 백오피스입니다. 1년간의 개발을 거쳐 서비스를 오픈했고, 이후 운영과 고도화를 이어갔습니다. 본인 커밋 3,720건으로 가장 많이 기여한 프로젝트입니다.

- 주문 관리 시스템
  - 고객이 주문한 제품을 관리하는 서비스입니다. 고객에 대한 정보, 제품 정보 등 확인하고 관리할 수 있습니다.
- 물류 관리 시스템
  - 네코아의 제품(정수기, 매트리스, 공기청정기, 자재 등)을 관리합니다.
  - 재고관리, 창고 간 제품 이동, 발주, 출고, 입고 등 물류 전반적인 시스템을 관리할 수 있습니다.
- 테크니션
  - 테크니션이 어느 위치, 시점에서 일하는지 일정을 확인하고, 관리자는 작업을 배정할 수 있습니다.
- 회계
  - 전표, 원장, 합계잔액 시산표, 반제 기능으로 미국 법인의 회계 업무 프로세스를 지원합니다.
- 시스템
  - 공통 코드 관리, 권한관리 등의 서비스를 제공합니다. 또한 넷마블의 챗봇 연동이 되어 직원들에게 업무 가이드를 보다 편리하게 제공합니다.

## 기술스택

---

- React, TypeScript, TanStack Query, Recoil, MUI, React Hook Form, react-big-calendar, openapi-typescript, Emotion, Sentry, Vitest, Vite, AWS EC2

## 개발내용

---

**서비스 개발**

- WMS의 출고 리뉴얼(배차), 창고이동, 실시간 재고 추적과 승인 프로세스를 개발해 출고부터 입고까지의 물류 흐름을 어드민에서 제어하는 환경을 구축했습니다.
- 창고 및 테크니션 재고실사를 4단계 워크플로우로 구현하고 재고 조정 화면을 개발했습니다.
- Shopify, OMS, AR 데이터를 3단계로 맞춰 보는 대사 화면과 전표/원장/합계잔액 시산표/반제 기능, 엑셀 다운로드를 개발해 회계 업무 프로세스를 구축했습니다.
- react-big-calendar 기반 테크니션 배정판, 잔여 시간 기반 자동 배정 결과 UI, 당일 긴급배정 기능을 개발했습니다.
- 전자결재 1차 개발과 Google Sheet 연동·에러 로그 추적이 가능한 주문/물류 실시간 모니터링 대시보드를 개발했습니다.
- Contents 라이브러리, OMS 주문 필터·추천 주문, 재무(주문결제현황·결제추적), 이메일 수신거부 화면을 개발했습니다.
- 기획 요청에 대해 적극적으로 조율하고 효율적인 화면 구성을 제안해 불필요한 개발 이슈와 지연 이슈를 줄였습니다.

**렌더링 이슈 및 코드 최적화**

- 기획, BE, FE 팀과 협력하여 BE API 구조와 호출 순서를 최적화했습니다.
- 화면 진입 시 동시에 호출되던 API를 초기 진입용과 사용자 액션 이후용으로 나누고 Query Key, `staleTime`, `enabled` 조건을 정리했습니다.
- **주요 화면 응답 기준, TanStack Query 캐싱과 호출 순서 최적화로 중복 호출을 제거해 화면 지연을 약 3초에서 1초로 단축했습니다.**
- **API 호출 순서 및 Lazy loading과 Suspense, 컴포지션 패턴을 활용해 FCP를 개선했습니다.**

**공통 컴포넌트와 전역 레이아웃**

- 팀이 공동으로 구축한 공통 컴포넌트 78종 체계에 223커밋을 기여하고, ButtonGroup, TimePicker, VirtualMultiSelect 등 신규 컴포넌트를 추가했습니다.
- **Table, DefinitionList, TextField, Accordion 등 핵심 컴포넌트 개선을 주도해, Table 개선 한 번이 246개 화면 파일에 일괄 반영되는 구조를 만들었습니다.**
- 앱 셸, TabMenu, Interceptor, ErrorElement 등 전역 layout 개발을 주도했습니다.

**SNB 영역 공통화**

- 화면마다 제각각이던 SNB 로직을 공통 훅으로 통합했습니다.
- **물류 도메인 공통 훅 `useSnb`·`useSnbRow`(각 8개 화면)와 메뉴별 필터를 저장하는 `usePersonalSnbSearch`(12개 화면)를 신규 개발했고, SNB 관련 커밋은 95건입니다.**

**개발 생산성 증대**

- FSD, Composition 아키텍처를 사용하여 코드 유지보수성을 강화했습니다.
- **50개 이상의 화면에서 공통으로 사용되던 컴포넌트를 ‘react-hook-form’ 기반의 단일 템플릿으로 통합하여 개발 기간을 단축하는데 기여했습니다.**
- Details 공통 화면 모듈화와 query params 기반 API 호출 제어로 코드 복잡도를 줄였습니다.
- 메뉴별 다국어 리소스 분리 로딩과 RBAC 기반 권한 처리를 적용했습니다.

**Sentry를 활용한 에러 트래킹**

- Sentry를 통해 스테이징 환경에서 발생하는 타입 에러 및 비정상적인 API 호출을 검출했습니다.
- Jira에 기록하고 팀 내에서 신속히 공유함으로써 에러 수정 시간을 단축했습니다.

**개발 문화 개선**

- 프로젝트의 코드 컨벤션을 수립하고 적용하여 코드 일관성을 확보했습니다.
- GitHub 코드 오너 추가 및 PR 리뷰 프로세스를 도입하여 코드 품질을 개선했습니다.
- husky, commitlint를 활용하여 컨벤션에 부합하지 않은 코드의 푸시를 방지하는 프로세스를 만들었습니다.
- 기술 적용 전 기본 동작 예제 코드를 Example 페이지로 작성해 팀 내 비슷한 기능 개발 시 참고할 수 있게 했습니다.
- 개발 및 스테이징 환경에서 기획자가 즉각적인 피드백을 줄 수 있도록 Google Sheets와 연동해 기획과 개발 간의 커뮤니케이션 창구를 만들었습니다.

## 성장경험

---

1. `openapi`를 활용하여 개발 시간 단축.
   1. `openapi-typescript` 를 사용하여 타입을 BE가 제공해주는 yaml 파일을 변환하여 사용하므로, 타입 작성 및 변환하는 시간을 단축할 수 있었습니다.
   2. FE, BE의 enum 코드를 맞추어 코드를 일관성 있게 사용할 수 있도록 했습니다. BE가 잘못 내려주거나 오타 등 같이 확인할 수 있어 상호간의 코드 품질을 높일 수 있었습니다.
2. FSD 디자인 패턴 경험
   1. 대메뉴(OMS, WMS, 테크니션, 모니터링, 대시보드 등)와 하위 중메뉴들을 관리할 수 있는 아키텍처가 필요했고, 이에 FSD 패턴을 적용하였습니다.
   2. 컴포넌트 및 훅 유닛 테스트가 용이하도록 컴포넌트를 구성할 수 있었습니다.
   3. 유사한 템플릿을 갖추고 있어 최대한 공통 컴포넌트로 추출하는 개발 방식 적용하였고, 이를 공통 개발 방식 룰셋으로하여 개발 속도를 향상시킬 수 있었습니다.
3. 공통화의 파급력
   1. 공통 컴포넌트와 SNB 훅을 개선하면 한 번의 수정이 수백 개 화면에 반영된다는 점에서, 공통 코드의 변경은 영향 범위를 먼저 확인하고 신중하게 진행해야 한다는 것을 배웠습니다.
4. 테스트 코드
   1. util함수와 컴포넌트, 훅에 대한 테스트코드를 작성하여 코드의 안정성을 높이려 했습니다. 그 결과 stg에서 발생하는 지라 이슈를 줄일 수 있었습니다.
5. 다양한 메뉴 개발
   1. WMS, 테크니션, 회계 및 기타 시스템 관련된 기능을 개발하며 다양한 도메인에 대한 견문을 높일 수 있었습니다.
   2. 기획과 개발자간의 빠른 소통으로 더 나은 UI/UX를 제안하고 피드백 받으며, 서비스의 품질을 보다 높일 수 있었습니다.

## 트러블 슈팅

---

**Situation**

1. 서비스 안에서 사용되는 공통코드 간 관계를 설정하는 N:N의 관계성을 잇는 화면 개발 요구가 있었습니다.
   1. 관계 코드를 추가할 때마다 새로운 객체를 생성하는 함수형 프로그래밍 방식으로 설계했습니다.
   2. 화면 상태를 recoil의 selector로 세분화해 개발을 진행했습니다.
   3. 이벤트마다 화면 리렌더링 성능 이슈가 발생했고, 잘게 나뉜 recoil selector 때문에 소스 흐름을 분석하기도 어려웠습니다.

**Task**

1. 설계의 근본적인 문제점을 파악해야 했습니다.
   1. react hook form과 연관된 리렌더링 이슈와, 이벤트가 발생할 때마다 화면 전체가 다시 렌더링되는 성능 이슈의 원인을 분석했습니다.

**Action**

1. 설계 방식을 변경했습니다.
   1. selector로 흩어져 있던 로직을 커스텀 hook으로 모으고, js 동적 바인딩(얕은 복사)을 통해 리턴된 객체에 children을 초기화하는 방식으로 바꿨습니다.
   2. 재귀 함수를 활용하여 children에 따른 node 객체를 생성하도록 했습니다.

**Result**

1. 매번 새 객체를 만들던 구조를 얕은 복사 기반으로 바꿔 리렌더링 성능 이슈를 해결했습니다.
2. 재귀 함수와 커스텀 훅으로 로직을 한곳에 모아 비즈니스 로직을 파악하기 쉬워졌고, 훅 단위로 테스트 코드를 작성하기도 이전보다 수월해졌습니다.
