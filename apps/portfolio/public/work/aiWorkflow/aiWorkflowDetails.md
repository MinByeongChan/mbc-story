# AI 에이전트 기반 개발 업무 개선

2026.01 – 현재

## 서비스 내용

---

Claude Code 기반 AI 스킬과 사내 문서 RAG를 만들어 반복적인 프론트엔드 개발 업무를 개선하는 AX 과제입니다. 실제 운영 프로젝트에 적용해 결과를 수치로 검증하는 것을 기준으로 삼았습니다.

- 라이브러리 마이그레이션, 피그마 퍼블리싱처럼 반복되는 개발 업무를 단계가 정해진 AI 스킬로 만듭니다.
- 화면설계서, 회의록, 인수인계 문서를 로컬 RAG로 묶어 Claude Code가 MCP로 업무 문맥을 검색하도록 합니다.
- 프로젝트 생성·구조 정리, 데일리 리포트, 회의록 작성처럼 개발 주변 업무를 도구로 자동화합니다.

## 기술스택

---

- Claude Code, AI Agent(Skill), MCP, ChromaDB, TypeScript, Node.js, node-cron, Gemini API

## 개발내용

---

**migrate-lib 스킬 — 라이브러리 마이그레이션 자동화**

- 영향도 분석, 기준 테스트 작성, 변환, 결과 검증까지 라이브러리 마이그레이션을 6단계로 나눈 스킬을 개발했습니다.
- 배정관리툴의 Recoil→Zustand 전환에 실전 적용하며, 변환 중 발견한 의존성·상태 책임 오류를 스킬 규칙에 다시 반영했습니다.
- **유닛 테스트를 49개에서 71개로 늘리고(신규 22개, 100% 통과) 에러 경로 커버리지를 0건에서 9건으로 확보했습니다.**
- **consumer 21개 파일을 수정하지 않고 상태 관리 라이브러리를 교체해 회귀 0건으로 이관했고, QA에서 잡히지 않던 개발 미스 약 6건을 찾아냈습니다.**

**frontend-publishing 스킬 — 피그마 퍼블리싱과 수렴 검증 루프**

- 피그마 시안과 기존 퍼블리싱 소스를 함께 참고해, 페이지 전체가 아닌 컴포넌트 단위로 퍼블리싱하는 방식을 제안했습니다.
- 기존 컴포넌트를 우선 재사용하는 원칙과 시안·렌더링 결과를 비교하는 검증 기준을 스킬에 넣었습니다.
- **버전별 테스트와 고도화를 거쳐 신규 SCSS를 898줄에서 165줄로 82% 줄였고, 수렴 검증 루프가 버전마다 이슈 3~5건을 자동으로 찾아내도록 했습니다.**
- design-to-component, design-component-classify 스킬을 함께 개발해 디자인 요소를 컴포넌트 단위로 분류했습니다.

**사내 문서 로컬 RAG(dt-rag)**

- 화면설계서, 회의록, 인수인계 문서, 업무 용어를 ChromaDB에 벡터화하고 Claude Code가 MCP로 관련 문맥을 검색하도록 구성했습니다.
- 증분 동기화 오케스트레이터와 node-cron 기반 sync 데몬을 만들어 문서 변경분이 자동으로 반영되게 했고, 사내 SSL(CA) 환경에도 대응했습니다.
- **청킹 방식을 개선해 512토큰 한계를 넘던 청크를 0개로 만들고, 바이너리 문서 인덱싱을 추가해 인덱싱 대상을 124건에서 346건으로 늘렸습니다.**
- 테스트 케이스 초안, 인수인계 누락 확인, 회의록·용어 정리에 활용하고, 검색 결과는 원문과 실제 서비스 동작을 기준으로 다시 검토했습니다.

**개발 주변 업무 자동화 도구**

- fe-project-starter: 프로젝트를 새로 만들거나(create) 기존 구조를 정리하는(restructure, transform) 파이프라인을 개발했습니다. 계획 기반으로 프로젝트 종류를 판정하고 변환 시 동작을 보존하는 장치를 넣었고, 사내 발표를 진행했습니다.
- 데일리 리포트 메일러: Jira, GitHub, Datadog, Obsidian 기록을 수집해 Gemini로 요약하고 메일로 발송하는 도구를 구축했습니다.
- 회의록 STT 도구: 오디오를 업로드하면 백그라운드 job runner가 전사하는 SPA를 개발하고, 사내 CA와 오프라인 모드에 대응했습니다.

## 성장경험

---

1. AI 도구는 결과를 수치로 검증할 수 있을 때 팀이 신뢰한다는 점을 확인했습니다. 마이그레이션 스킬을 테스트 수, 회귀 건수, 변경 파일 수로 평가한 것이 실제 운영 프로젝트 적용으로 이어졌습니다.
2. 반복 업무를 스킬로 만들 때는 한 번에 완성하기보다 실제 적용에서 발견한 오류를 규칙으로 되돌리는 루프가 품질을 결정한다는 것을 경험했습니다.
3. RAG는 모델보다 문서를 어떻게 자르고 어떤 문서를 넣는지가 검색 품질을 좌우한다는 점을 청킹 개선 작업으로 확인했습니다.

## 트러블 슈팅

---

**Situation**

1. Recoil에서 Zustand로 상태 관리 라이브러리를 교체해야 했지만, 수십 개의 Atom과 Selector가 화면 곳곳에 얽혀 있어 AI가 코드를 변환하면 기존 동작이 조용히 바뀔 위험이 있었습니다.
2. 사내 문서 RAG에서 일부 청크가 임베딩 모델의 512토큰 한계를 넘어(최대 565토큰) 뒷부분이 잘린 채 저장되고, 바이너리 문서는 인덱싱 대상에서 빠져 있었습니다.

**Task**

1. 변환 결과가 맞는지를 사람의 눈이 아닌 테스트로 판단할 수 있는 구조가 필요했습니다.
2. 잘리는 청크 없이 문서 전체가 검색되도록 청킹 기준과 인덱싱 범위를 다시 잡아야 했습니다.

**Action**

1. 변환 전에 기존 동작을 그대로 기록하는 Characterization Test를 먼저 작성하고, Zustand Store를 기존 Recoil 인터페이스 뒤에 두는 strangler 브리지 패턴으로 wave 단위 이관을 진행하도록 스킬 단계를 설계했습니다.
2. 청크 크기와 분할 기준을 조정해 토큰 한계를 넘지 않도록 하고, 바이너리 문서도 텍스트로 추출해 인덱싱하도록 확장했습니다.

**Result**

1. **유닛 테스트 49개→71개, 에러 경로 커버리지 0건→9건, consumer 21개 파일 무변경, 회귀 0건으로 이관했습니다.** 기준 테스트 덕분에 QA에서 잡히지 않던 개발 미스 약 6건도 찾아냈습니다.
2. **85개 청크 실측 기준 최대 369토큰으로 512토큰 초과 청크가 0개가 되었고, 인덱싱 대상은 124건에서 346건으로 늘었습니다.**
